## What this repository actually is

This repo contains **two unrelated layers**, not a single application:

1. **The real FinOps Lab product** — an npm-workspaces monorepo (`apps/`, `packages/`, `infra/bicep`) implementing the v1 "Connect Azure" onboarding flow. This is where active development happens.
2. **Planning artifacts** for the product, organized by tier under `docs/`:
   - Shared/cross-tier, at `docs/` root: `architecture.md` (canonical per-layer infra choice + build status across both tiers), `byoc-review-and-tier-comparison.md` (session notes on the BYOC review and tier-prioritization decision), `frontend-design-decisions.md` (running log of `apps/web` UI/UX decisions, applies regardless of tier), `initial-vision-archive.md` (a consolidated, explicitly-historical snapshot of the founder's original pre-build vision — superseded, kept for reference only).
   - `docs/byoc/` — BYOC-tier docs. `connect-azure.md` (current, authoritative, the tier that actually ships) and `cost-dashboard-frontend.md`, `azure-cost-management-endpoints.md`, `azure-resource-inventory.md` (every Azure resource `infra/bicep` provisions, with names/properties, verified against the actual `.bicep` source), `clerk.md` (Clerk application setup — Organizations/session-token config — plus how to manually look up a specific customer's paired backend URL + API key from Clerk private org metadata for support/debugging) document what's built; `docs/byoc/plan/` holds not-yet-built BYOC work (`cost-management-429-resilience.md` — Phase 1 pre-launch 429 guardrail + Phase 2 deferred synced-cost-history fallback; `finalize-byoc-flow.md` — local/real-Azure verification pass).
   - `docs/saas/plan/cloudguard-hosted.md` — SaaS-tier architecture, decisions locked but the tier itself is deferred post-v1, see below.

   Not part of the shipped product.

(The repo used to also carry a generic, unfilled Terraform/Makefile/.azuredevops template left over from the starter repo it was cloned from — removed as dead weight; it never shared config or CI with the monorepo above. `.github/workflows/build-api-image.yml` is real, active CI though — it builds/pushes `apps/api-byoc`'s Docker image to GHCR, which `infra/bicep/main.bicep` deploys by default.)

## Scope decision: v1 ships BYOC-only

As of 2026-08-06, initial shipping is **BYOC-only** — the flow already built and documented in `docs/byoc/connect-azure.md` (Bicep "Deploy to Azure" + Managed Identity), stuck with deliberately because it needs zero FinOps Lab-owned Azure infrastructure and reuses 100% of already-shipped work. Two things are explicitly deferred, not abandoned:

- **The SaaS tier** (a separate centrally-hosted multi-tenant backend on Railway/Neon, cross-tenant Azure access via a FinOps Lab-owned multi-tenant App Registration) — architecture is fully designed and locked in `docs/saas/plan/cloudguard-hosted.md`. A scaffold (`apps/api-saas`: health endpoint, `Tenant`/`AzureConnection` schema with Row-Level Security shipped and verified) existed and was removed from the working tree before the connection/consent flow was built — preserved in git history at commit `335dde2`, not part of the current codebase. Revisit after initial customer traction.
- **A manual-credential onboarding path for BYOC** — for customers who self-host `apps/api-byoc` outside Azure-managed compute (on-prem, another cloud), where Managed Identity has nothing to resolve. Not yet specified or built; `apps/api-byoc/src/azure/azure-credential.provider.ts` today only supports Managed Identity and `az login`, no `ClientSecretCredential` path.

## Architecture (v1 — customer-hosted, no FinOps Lab backend)

The core architectural decision, documented in **`docs/byoc/connect-azure.md`** (read this before touching the connect flow — it is the source of truth and supersedes the older Service-Principal/shared-backend version of the doc):

- FinOps Lab has **no backend or database of its own**. A customer provisions the backend + Postgres directly **inside their own Azure tenant** via a "Deploy to Azure" button (ARM/Bicep). FinOps Lab only hosts the frontend centrally (Next.js, intended for Vercel).
- The deployed backend authenticates to Azure Cost Management / Resource Graph via a **system-assigned Managed Identity** — no client secret is ever entered, stored, or transmitted (this replaced an earlier cross-tenant `ClientSecretCredential` design).
- Isolation between customers is **physical** (one Postgres instance per deployment), not row-level — there is no multi-tenancy scoping column in the schema.
- The frontend pairs with a customer's deployed instance via a `Backend URL` + `API key` (shown once as a deployment output), stored in **Clerk private organization metadata** — deliberately not a FinOps Lab-side database, and deliberately not Clerk *public* metadata (which is client-readable). All reads/writes of the pairing happen server-side.

### Monorepo layout

```
apps/api-byoc/       NestJS backend — the code deployed into the customer's tenant (BYOC, ships)
apps/web/       Next.js frontend — the only thing FinOps Lab hosts centrally
packages/shared/  Zod schemas + types shared by both apps (built to dist/, consumed as a normal compiled workspace dependency — not source-transpiled by either bundler)
infra/bicep/    The "Deploy to Azure" template
```

(A SaaS-tier backend, `apps/api-saas`, previously lived here too — see "Scope decision" above and "SaaS tier" below for where it went.)

**`apps/api-byoc`**'s *documented* contract (see `docs/byoc/connect-azure.md`) is exactly 5 endpoints — `GET /health`, `GET /subscriptions`, `POST /subscriptions/select`, `GET /status`, `POST /sync` — behind a single global API-key guard (`src/auth/api-key.guard.ts`, registered as `APP_GUARD`), applied to *every* route including `/health`. One Prisma model, `Instance` (`prisma/schema.prisma`) — a singleton row per deployment, fetched/created via `InstanceService.getOrCreate()`, never looked up by a caller-supplied ID. Azure calls go through `src/azure/`: `AzureCredentialProvider` picks `DefaultAzureCredential` (production, resolves the Managed Identity) or `AzureCliCredential` (local dev, requires `az login`) based on `AZURE_AUTH_MODE`. `/sync` is synchronous and re-entrancy-locked in-memory (`SyncService`) — this is only correct because the Container App is pinned to `minReplicas=maxReplicas=1` in the Bicep template; don't scale it without revisiting that lock and the migration-on-boot strategy below.

**`src/costs/`** adds 4 more GET endpoints beyond that documented contract — `/costs/daily`, `/costs/accumulated`, `/costs/by-service`, `/costs/by-resource` — built ahead of real dashboard/frontend work, not yet reflected in `docs/byoc/connect-azure.md`. All route through `CostManagementService` (`src/azure/cost-management.service.ts`), which wraps Azure's single `client.query.usage()` SDK call with different `dataset.grouping`/`granularity` per view, plus an in-memory 30-minute cache (reported via an `X-Cache: HIT`/`MISS` response header — `main.ts`'s CORS config needs `exposedHeaders` for any new header like this to be readable by browser JS). `/costs/accumulated` makes **no Azure call of its own** — it's a derived running-sum transform of `/costs/daily`'s (cached) data, so the two endpoints share one cache entry. Two Azure-specific gotchas baked into `customDateRange()`: (1) Azure rejects a `to` timestamp containing today's exact time-of-day as "in the future" (same-day data isn't fully processed) — dates are normalized to UTC-midnight boundaries, never the literal current instant; (2) the Custom timeframe is inclusive on both ends, so "last N days" means `today - (N-1)`, not `today - N`. Cost Management's throttling (`429 Too many requests`) is scoped **per subscription being queried, not per calling identity** — confirmed empirically; switching Azure identities doesn't grant a fresh quota against the same subscription, so the cache (not identity-juggling) is the real mitigation. `dev-test/viewer/index.html` is a standalone, dependency-free HTML page for exercising these 4 endpoints outside the real frontend — serve via `npx http-server dev-test/viewer -p 5500` (requires `http://localhost:5500` present in `apps/api-byoc/.env`'s comma-separated `FRONTEND_ORIGIN`).

**`infra/bicep`** is deployed at resource-group scope (all the Azure Portal's "Deploy a custom template" flow allows), but the Reader + Cost Management Reader role assignments must be subscription-scoped — `modules/role-assignments.bicep` declares `targetScope = 'subscription'` and is invoked from `main.bicep` with an explicit `scope: subscription()`, a real Bicep feature (a module's scope can differ from its parent deployment's). Prisma migrations run from `apps/api-byoc/docker-entrypoint.sh` at container boot (`prisma migrate deploy`), not from CI — there is no pipeline that reaches into a customer's tenant.

**`apps/web`**'s `/connect-azure` page composes: a deploy-link button (built from `NEXT_PUBLIC_BICEP_TEMPLATE_URI`) → `PairingForm` (posts to `app/api/instance/route.ts`, which calls the paired backend's `/health` before persisting) → `OnboardingStepper` (discover/select/sync against `app/api/instance/subscriptions/route.ts` and `.../sync/route.ts`). All three of those route handlers are the *only* code allowed to read/write the pairing (`lib/clerk-org-metadata.ts`, marked `server-only`) or call the customer's backend (`lib/backend-client.ts`, also `server-only`) — client components only ever see a redacted `apiKeyLast4`. Note: `OnboardingStepper` collapses any non-OK response from these route handlers into a generic error ("Could not discover subscriptions", etc.) — the real cause (backend unreachable, Azure auth failure, whatever) is swallowed client-side; check `apps/api-byoc`'s own logs when diagnosing, not just the browser error text.

**`apps/web/app/dashboard`** is the ongoing product surface (as opposed to `/connect-azure`'s one-time onboarding), proxying `apps/api-byoc`'s 4 `/costs/*` endpoints through the same two-layer pattern as onboarding: `lib/backend-client.ts` methods → `app/api/instance/costs/{daily,accumulated,by-service,by-resource}/route.ts` (auth check → pairing lookup → backend call), never the customer's API key reaching the browser. `app/dashboard/layout.tsx` is shared chrome (nav, subscription switcher, period selector) around `page.tsx` (Overview: 3 KPI tiles + accumulated hero chart) and one detail page per view (`daily/`, `by-service/`, `by-resource/`). Two URL search params, not React state, drive filtering everywhere — `?subscriptionId=` and `?days=` — so every page is server-rendered/bookmarkable and filters persist across nav; `PeriodSelector`/`SubscriptionSwitcher` (`components/dashboard/`) just push new query strings. `SubscriptionSwitcher` deliberately filters the full Azure subscription list down to only `Instance.selectedSubscriptionIds` — `/costs/*` has no synced context for a subscription that was never selected during onboarding, so unselected ones aren't offered; if a customer paired more subscriptions than they see in the dropdown, that's this filter, not a bug — the fix is re-running subscription selection, not the component. The Overview page (`app/dashboard/page.tsx`) fetches `dailyCosts({ days: days * 2 })` once and derives both the prior-period delta and the accumulated/cumulative series from that single response client-side, rather than making 3 separate Azure-backed calls. Charting is Recharts (`^3.10.1`) — note its exported `Tooltip` is **not actually generic** despite `TooltipContentProps<Value,Name>` being a parameterizable type alias in the `.d.ts` files; `<Tooltip<number,string>>` JSX generic instantiation fails with "Expected 0 type arguments, but got 2". This project went through two narrower fixes for the `content` prop's assignability across this session's dependency bumps (explicit unparameterized, then explicit `TooltipContentProps<number,string>` on both the callback and a separate `ChartTooltip` component) and **both eventually broke again** on an unrelated dependency-tree shuffle elsewhere in the workspace, without any change to the chart code itself — evidence this specific generic-inference boundary is fragile against the exact resolved type-package versions, not something to trust as permanently fixed. The current, more robust pattern in all 4 `components/dashboard/*-chart.tsx` files sidesteps the boundary entirely: the `content={(props) => ...}` callback is left with an **inferred, unannotated parameter** (never re-declare its type), and it renders a separate `ChartTooltipBody` component typed with **plain, already-extracted values** (e.g. `{ label: string; value: number; currency: string }` or `{ point: ResourceCost; currency: string }`) — never recharts' own prop types — so there is no cross-type assignability check for a future dependency bump to break. Coerce values (`Number(props.payload[0]?.value ?? 0)`, `String(props.label)`, `props.payload[0]?.payload as ResourceCost`) inline in the callback before handing them to the body component. Design tokens for charts live in a `.dashboard-root`-scoped CSS custom-property block in `globals.css` (light values + `@media (prefers-color-scheme: dark)` override, sourced from the `dataviz` skill's reference palette) — there is no manual theme toggle in this app, dark mode is OS-preference-only.

**Tailwind v4** (upgraded from v3): `globals.css` now starts with a single `@import "tailwindcss";` (replacing the three `@tailwind base/components/utilities` directives, which v4 no longer supports). `postcss.config.js` uses the `@tailwindcss/postcss` plugin (a separate package) instead of `tailwindcss` directly. `tailwind.config.ts` was deleted — it had nothing in it beyond default `content` globs and empty `theme.extend`/`plugins`, and v4's automatic content detection (scans the project respecting `.gitignore`) finds `app/**`/`components/**` correctly without it; verified by comparing compiled CSS output with and without the file present (byte-identical). `autoprefixer` was removed too — v4's Lightning CSS-based engine vendor-prefixes internally, and the built stylesheet was unchanged with it gone.

## SaaS tier — removed from working tree, preserved in git history

`apps/api-saas` is **not present in the codebase today.** It was scaffolded, then removed on 2026-08-07 while v1 focuses on finishing BYOC only — not abandoned, the code is fully recoverable from git history (checkpoint commit `335dde2`, before removal) and `docs/saas/plan/cloudguard-hosted.md` remains the source of truth for resuming it. Don't assume the directory exists; check history before referencing any file under it.

Summary of what existed at removal time, for whoever resumes this: a separate NestJS app, multi-tenant from the ground up (`Tenant` + `AzureConnection` Prisma models, no singleton-instance assumption like `apps/api-byoc`), with its own isolated Prisma client output (at the time, deliberately not the shared hoisted `node_modules/.prisma/client` `apps/api-byoc` used, to prevent the two schemas from overwriting each other's generated client — moot now that `apps/api-byoc` also generates to its own custom path, see below, though for an unrelated reason). `ClerkAuthGuard` verified the Clerk session JWT directly (no per-tenant API keys, unlike `apps/api-byoc`'s single global one — that pattern doesn't work once there's more than one tenant). Only `GET /health` was wired up; no connection flow, no cost endpoints, nothing reachable from `apps/web`.

**Row-Level Security was shipped and verified on `azure_connection`** (`enable_rls_azure_connection` migration) — the one piece of this tier that was genuinely done, not just scaffolded. The non-obvious part, worth knowing before resuming this schema: RLS is silently inert unless the connecting DB role lacks `BYPASSRLS`. Both the local Postgres bootstrap role *and* Neon's default `neon_superuser`-derived role have `BYPASSRLS` — so the app's runtime `DATABASE_URL` had to be a separately-created, restricted role (`local-dev-init.sql` set this up locally as `cloudguard_app`), while migrations used a different, elevated connection string via Prisma's `directUrl` (`MIGRATE_DATABASE_URL` in `.env`) — `prisma/schema.prisma`'s `datasource` block wired this split. Every tenant-scoped query went through `PrismaService.runInTenantContext()`, which set `app.tenant_id` transaction-locally (`set_config(..., true)`, never a bare `SET`, so it couldn't leak across a pooled connection).

`apps/api-byoc` has **no `dotenv` loading of its own** — `nest start` does not read `.env` files automatically, so the env vars above must actually be present in the shell's environment, not just sitting in `apps/api-byoc/.env`. `dev-test/test-dev.ps1` handles this correctly (parses `apps/api-byoc/.env` and exports each value into the child process it spawns) — but running `npm run dev:api`/`npm run start:dev -w apps/api-byoc` directly in a fresh shell that hasn't sourced those vars will boot the app *successfully* (Prisma 7's driver-adapter pattern no longer validates the connection string at `$connect()` — see below) and then fail with a cryptic `SASL: SCRAM-SERVER-FIRST-MESSAGE: client password must be a string` 500 on the first request that actually touches the database (e.g. `/status`). Check for a missing `DATABASE_URL` first if you see that exact error — it's an environment issue, not an application bug, just a much less obvious one than the old Prisma 5 behavior (which failed fast at boot with a clear `PrismaClientInitializationError`).

**Prisma 7 migration** (upgraded from 5.x): the connection URL moved out of `schema.prisma` entirely (no longer a valid `datasource.url` field) into `apps/api-byoc/prisma.config.ts`, and `PrismaClient` now requires an explicit driver adapter — `PrismaService`'s constructor passes `new PrismaPg({ connectionString: process.env.DATABASE_URL })` (`@prisma/adapter-pg` + `pg`), since Prisma 7 dropped the implicit Rust query engine. The generator block now uses `provider = "prisma-client"` (renamed from `"prisma-client-js"`) with a required `output` path — this project generates to `apps/api-byoc/src/generated/prisma` (plain `.ts`, no native binary/WASM to worry about copying in Docker) and sets `moduleFormat = "cjs"` specifically to avoid converting the whole NestJS app to ESM, which the Prisma docs' own migration examples assume by default. Import the model type as `InstanceModel` (renamed from the old bare `Instance`) from `../generated/prisma/models`, not `@prisma/client`. One non-obvious build gotcha this surfaced: `prisma.config.ts` lives at the app root (Prisma's own convention, "alongside package.json"), and without excluding it, `nest build`/`tsc` would infer `rootDir` as the app root instead of `src/`, nesting the whole build output under `dist/src/...` and breaking `docker-entrypoint.sh`'s `exec node dist/main.js`. Both `apps/api-byoc/tsconfig.json` **and** `tsconfig.build.json` exclude `prisma.config.ts` (plus `node_modules`/`dist`/`test`) — `nest build` compiles via `tsconfig.build.json`, but `nest start --watch` reads `tsconfig.json` directly, and each needed the exclude independently; don't remove it from either. `docker-entrypoint.sh` itself needed no changes — `prisma migrate deploy --schema prisma/schema.prisma` still works exactly as before, since Prisma CLI resolves `prisma.config.ts` from cwd (which the Dockerfile's `WORKDIR` and `-w apps/api-byoc` npm scripts already put it in).

**`nest start --watch` intermittent `Cannot find module '.../dist/main'` crash — root-caused and fixed, not a permanent quirk.** This looked non-deterministic for a long time (retry loops and settling delays helped inconsistently; an SWC builder swap didn't help at all) because the trigger wasn't what it looked like. The real cause: `tsconfig.json`'s `incremental: true` wrote its build-info cache (`tsconfig.build.tsbuildinfo`) to the app root by default — *outside* `dist/` — while `nest-cli.json`'s `deleteOutDir: true` only clears `dist/` itself. So the cache could survive a `dist/` wipe: tsc would read the stale cache, conclude nothing needed recompiling, print "Found 0 errors", and skip re-emitting entirely — leaving `dist/` empty (or partially written) while claiming success, and the runner would then fail to find (or fail to fully resolve) the entry point. Fixed at the config level: `tsconfig.json` sets `"tsBuildInfoFile": "dist/tsconfig.build.tsbuildinfo"`, so the cache now lives inside `dist/` and gets wiped in lockstep with it on every invocation — reproduced the failure at a consistent rate before this fix, then got a clean run every time after it. If you ever see a `dist/`-related "file exists per the compiler but the runtime can't find it" symptom on a `tsconfig.json` with `incremental: true`, check where `tsBuildInfoFile` actually points before assuming it's a timing race.

**`prisma.config.ts` does not auto-load `.env`.** Unlike Prisma's legacy CLI behavior, `env()` inside `prisma.config.ts` reads only from `process.env` — running `npx prisma studio` (or any Prisma CLI command) from a fresh shell with no vars pre-exported fails with `PrismaConfigEnvError: Cannot resolve environment variable: DATABASE_URL`, even from the correct cwd. Fixed by adding `import "dotenv/config";` as the first line of `prisma.config.ts` — safe everywhere else too, since `dotenv` never overrides an already-set env var (Container Apps/`docker-entrypoint.sh`/the NestJS app itself all already have `DATABASE_URL` as a real env var, and no `.env` file even ships in the Docker image for `dotenv` to find).

**TypeScript 6 migration** (attempted 7.0.2, landed on 6.0.3): TypeScript 7.0's `tsc` binary works, but `nest build`/`nest start --watch` need the compiler's *programmatic* API, which 7.0 doesn't expose yet — NestJS's own CLI refuses to run with a clear error ("expected to return in 7.1... install TypeScript 6 until then"). 6.0.3 (latest stable 6.x) is the actual current ceiling for this stack, and it happens to also be the newest version `typescript-eslint@8.67.0` (pulled in by `eslint-config-next`) declares support for (`<6.1.0`) — a second, independent reason not to force 7.x. Real breaking changes hit going 5→6, both from TS6's stricter config validation: `moduleResolution: "node"` (the old alias for the now fully-removed `node10`) had to become `"node16"` in `tsconfig.base.json`, which in turn *requires* `module` to also be `"node16"` (TS6 error: "Option 'module' must be set to 'Node16' when option 'moduleResolution' is set to 'Node16'") — this still emits plain CommonJS for every workspace here since none of them set `"type": "module"` in `package.json`, so it's a config-shape change only, not a runtime one. And `baseUrl` is deprecated (removed in a future TS7): dropped entirely from `apps/api-byoc/tsconfig.json` (nothing there used it — no non-relative imports) and from `apps/web/tsconfig.json` too, where it looked load-bearing for the `@/*` path alias but wasn't — modern TypeScript resolves `paths` without an explicit `baseUrl` by defaulting to the tsconfig's own directory; verified with a full build both before and after removing it.

**Lint pipeline rebuild** (uncovered by finally running `npm run lint -w apps/web` for the first time since the earlier Next.js 16 + `eslint@10.8.1` bump, not caused by the TypeScript work itself): three independent breakages, in order encountered — `next lint` is gone entirely from Next.js 16's CLI (`next --help` lists no `lint` subcommand at all), so `apps/web/package.json`'s `lint` script now runs `eslint .` directly against a new flat `apps/web/eslint.config.js` (the old `.eslintrc.json` was deleted — ESLint 10 dropped legacy-config support outright, flat config is the only format). `eslint-config-next@16.3.1` exports a ready-made flat-config array at `eslint-config-next/core-web-vitals` — no `FlatCompat` shim needed. Second: `eslint@10.8.1` itself crashed two different ways against the current `eslint-plugin-react@7.37.5` (latest published — not a version-pinning fix) and separately inside ESLint's own `SourceCode.finalize()` — both stem from ESLint 9+ removing `context.getFilename()` (now the `context.filename` property) and related internal API changes that this plugin generation hasn't fully caught up with; downgraded to `eslint@9.39.5` (still satisfies `eslint-config-next`'s own declared `>=9.0.0` peer range) and both crashes disappeared. Third, once lint actually ran, `eslint.config.js` sets `settings.react.version` explicitly (keep this in sync with the installed `react` version) since `eslint-plugin-react`'s auto-detection is what triggered the first crash above. With all three fixed, lint surfaced 22 genuine findings from two new React Compiler-era rules in `eslint-plugin-react-hooks@^7.0.0` (`react-hooks/error-boundaries`, `react-hooks/immutability`) that don't fit this codebase's Server Component patterns well (both rules assume client-side re-render/memoization semantics that don't apply to a function that runs once per request with no `"use client"`) — downgraded to `"warn"` in `eslint.config.js` with inline reasoning rather than restructuring five already-tested dashboard pages' error handling as a side effect of a dependency bump.

For real Azure calls locally, set `AZURE_AUTH_MODE=cli` and `az login` first — `DefaultAzureCredential` (the production path) only resolves inside a deployed Container App's Managed Identity. `.github/workflows/build-api-image.yml` tags `:latest` + `:<sha>` on every push to `main` (a moving target) and additionally tags an immutable `:X.Y.Z` on any `vX.Y.Z` git tag push (release convention — see `infra/bicep/README.md`'s "Releasing a new image version"). `main.bicep`'s `containerImage` default stays on `:latest` until a real release exists to pin it to.

No test framework (Jest/Vitest/etc.) is configured anywhere in the repo yet, but there is a lightweight smoke test: `npm run smoke-test -w apps/api-byoc` (`apps/api-byoc/scripts/smoke-test.mjs`) hits a running instance's `/health`, `/subscriptions`, `/status`, and one `/costs/daily` call given `BACKEND_URL`/`API_KEY` — run it against a candidate image before cutting a release tag. Deliberately skips `POST /subscriptions/select` and `POST /sync` (mutating, and `/sync` burns against Azure Cost Management's real per-subscription throttle).

## Clerk setup gotcha (apps/web)

See also `docs/byoc/clerk.md` for full setup steps plus how to manually look up a specific customer's paired backend URL/API key from Clerk private org metadata (support/debugging).

Clerk Organizations must be enabled with **"Membership required"** (every signed-in user needs an active org — `apps/web/proxy.ts` and every `app/api/instance/*` route read `(await auth()).orgId`). This is *not* enough on its own: a fresh Clerk application's session token does not include `org_id`/`org_role`/`org_slug` claims by default. If `orgId` is `undefined` even for a user with a real, confirmed organization membership (verified via the Clerk backend API showing `last_active_organization_id` set on the session), the fix is in the Clerk Dashboard, not the code: **Configure → Sessions → Customize session token**, add:
```json
{ "org_id": "{{org.id}}", "org_slug": "{{org.slug}}", "org_role": "{{org.role}}" }
```
Existing sessions pick this up automatically (tokens refresh every ~60s); no user-facing repro like signing out/in is actually required once the claim is added. `apps/web/app/layout.tsx` already renders `OrganizationSwitcher` + `UserButton` for local org creation/selection during dev.

**`@clerk/nextjs` v7 breaking changes** (hit during the Next.js 16 upgrade — `apps/web` is now on `@clerk/nextjs@^7.7.4`): `auth()` and `clerkClient()` both became async — every call site needs `await` (`apps/web/lib/clerk-org-metadata.ts` calls `await clerkClient()` before touching `.organizations`). `middleware.ts` is renamed `proxy.ts` per Next.js 16's file convention (the `clerkMiddleware()` export itself is unchanged). `SignedIn`/`SignedOut` were removed from `@clerk/nextjs` entirely — replaced by an async `<Show when="signed-in">` Server Component (`apps/web/app/layout.tsx`); there's no drop-in client-component equivalent, `Show` must be rendered from a Server Component context. `createRouteMatcher()` is deprecated upstream (in favor of per-route auth checks) but still functional — kept as-is in `proxy.ts` rather than refactored, a separate, larger change than the version upgrade itself.

**Next.js 16 auto-generates `apps/web/AGENTS.md` + `apps/web/CLAUDE.md`** on every `next dev`/`next build` (a new "agentRules" feature, source: `node_modules/next/dist/server/lib/generate-agent-files.js`) — disabled via `agentRules: false` in `apps/web/next.config.mjs` since this repo already has an authoritative, checked-in root `CLAUDE.md` and doesn't want a second, workspace-scoped one regenerating itself on every dev-server boot.

## Security note

An ARM/Bicep deployment `output` (the customer's API key, generated by `main.bicep`) is **not actually ephemeral** — it stays visible in the resource group's Deployment history to anyone with read access, despite `docs/byoc/connect-azure.md`'s "shown once" framing. This is a known, accepted v1 gap (see `infra/bicep/README.md`), not a bug to silently fix.
